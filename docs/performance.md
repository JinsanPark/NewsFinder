## 적재 성능

300건 적재 시 58초 소요. 요청 1건당 약 200 ms가 Voyage API 응답 대기 시간.
(기사 제목 + 요약 임베딩 기준)
`input` 파라미터가 배열을 받는 점을 이용해 128건씩 묶어 호출하도록 변경.

| | 요청 횟수 | 소요 시간 |
|---|---|---|
| 개선 전 | 300회 | 58.6초 |
| 개선 후 | 3회 | 3.5초 |

동일 데이터 기준 1회 측정. 네트워크 상황에 따라 변동 가능.

## 검색 성능

더미 기사 300건을 복제해 2,400건, 19,200건으로 늘려가며 측정.

| 방식 | 커밋 | 300건 | 2,400건 | 19,200건 |
|---|---|---|---|---|
| 캐시 없음 (매 검색마다 전건 조회 + 파싱) | [`c64e9bd`](https://github.com/JinsanPark/NewsFinder/commit/c64e9bd2b9e0b7a8c2a83118a8d1b9617c3e4828) | 225.3 ms | 427.2 ms | 2,136.8 ms |
| 자바 메모리 캐시 | [`d234a6a`](https://github.com/JinsanPark/NewsFinder/commit/d234a6aeb6224f504666894c63bcd84d4d84bb67) | 196.7 ms | 239.8 ms | 525.2 ms |
| pgvector | [`2ae30ab`](https://github.com/JinsanPark/NewsFinder/commit/2ae30abc6c47732c82fbca1910143c5b033691d5) | 196.8 ms | 211.2 ms | 287.4 ms |
| pgvector + HNSW 인덱스 | [`56f0197`](https://github.com/JinsanPark/NewsFinder/commit/56f01973929baad49f4891b3c9d543790236156e) + 인덱스 | — | — | 209.2 ms |

인덱스 측정은 19,200건만 수행.
응답 시간에는 검색어를 벡터로 바꾸는 Voyage API 왕복이 포함.

### 300건에서는 인덱스를 쓰지 않는 것이 맞음

`EXPLAIN ANALYZE`로 확인한 결과, 300건에서는 플래너가 HNSW 인덱스를 선택하지 않고 전건 스캔을 택함.
`WHERE` 절을 제거해도 동일하므로 쿼리 형태의 문제가 아니라 **데이터가 작아서** 내린 판단.

```
Seq Scan on news  (cost=0.00..37.75 rows=300)
Execution Time: 2.475 ms
```

`enable_seqscan = off`로 인덱스 사용을 강제하면 계획은 바뀌지만 훨씬 느려짐.

```
Index Scan using news_embedding_hnsw on news  (actual time=142.067..142.139 rows=10)
```

| | 시간 |
|---|---|
| Seq Scan (플래너 선택) | 2.475 ms |
| Index Scan (강제) | 142 ms |

약 60배 차이. 인덱스를 쓸 수 없는 상태가 아니라 쓰지 않는 쪽이 맞는 상황.
300건 규모에서는 HNSW 그래프를 타는 비용이 전건 스캔보다 큼.

강제 실행 시 `Execution Time`은 948 ms로 찍히지만 이 값은 비교에 쓸 수 없음.
`enable_seqscan = off`는 Seq Scan을 금지하는 것이 아니라 비용을 크게 올려 밀어내는 방식이라,
그 과정에서 평소에는 실행되지 않는 작업(JIT 컴파일 255 ms)까지 함께 붙었음.
인덱스 자체의 비용은 Index Scan 노드 시간으로 봐야 함. 강제 실행은 1회 측정.

19,200건에서 287.4 -> 209.2 ms로 줄어든 것은 인덱스가 사용된 결과로 보이나,
해당 규모에서는 아직 실행 계획을 확인하지 않음.

### 검색 한 번의 구성 (300건, 캐시 도입 전)

전체 응답은 브라우저 Network 탭 기준, API 구간은 서버 내부 측정, 쿼리 실행은 `EXPLAIN ANALYZE` 기준.

| 구간 | 시간 | 비중 |
|---|---|---|
| Voyage API 왕복 (검색어 임베딩) | 197.1 ms | 87% |
| 앱↔postgres 왕복, 1024차원 벡터 전송, 결과 매핑, 렌더링 | 약 28 ms | 12% |
| DB 쿼리 실행 | 2.5 ms | 1% |
| 합계 | 226.4 ms | |

**DB가 계산에 쓰는 시간은 전체의 1%임.**
별도로 `SELECT 1`을 실행한 왕복 기준선은 약 7 ms (DBeaver 기준, 클라이언트가 달라 정밀 비교는 아님).

이 규모에서는 계산 방식(자바 / pgvector / 인덱스)을 바꿔도 얻을 수 있는 여지가 거의 없음.
300건 구간에서 세 방식이 196~225 ms로 비슷했던 이유이기도 함.

> 이 표는 2026-08-28 측정. API 왕복은 2026-09-03 재측정에서 184.8 ms가 나왔음.
> 두 번째 줄의 '약 28 ms'는 차감으로 얻은 값이고 그 안에서 DB 왕복을 분리하지 않았는데,
> 재측정에서 DB 히트 경로가 15.2 ms로 나왔음.

### 건당 비용

API 왕복은 건수와 무관한 고정 비용이므로, 두 지점의 차이로 산출.

```
(19,200건 값 − 2,400건 값) ÷ 16,800
```

| 방식 | 건당 |
|---|---|
| 캐시 없음 (조회 + 파싱 + 계산) | 101.8 μs |
| 자바 캐시 (계산만) | 17.0 μs |
| pgvector (DB 스캔) | 4.5 μs |

셋 다 전건 스캔이므로 O(n). 상수만 다름.

단, 이 산출은 두 지점의 차이에서 API 왕복이 상쇄된다는 전제 위에 있는데,
두 측정이 같은 세션이 아니라면 API 변동(183~197 ms 관측)이 그 차이에 남음.
차이가 클수록 영향이 작아지므로 캐시 없음(1,709.6 ms)은 견고하지만,
**pgvector는 두 지점 차이가 76.2 ms에 불과해 4.5 μs를 단정하기 어려움.**

## 검색어 벡터 캐시

한 번 만든 검색어 벡터를 DB에 저장해 재사용.
`(정규화된 검색어, 모델명)`을 키로 조회하고, 캐시에 있으면 API를 호출하지 않음.
검색어는 `NFC -> 앞뒤 공백 제거 -> 연속 공백 축약 -> 소문자` 순으로 정규화하며, 키와 API 입력에 같은 문자열을 사용.

모델명을 키에 포함시킨 이유는, 모델을 교체했을 때 이전 모델이 만든 벡터가 조용히 재사용되는 것을 막기 위함.
차원 수만 같으면 유사도 계산이 오류 없이 수행되므로 결과만 어긋나고 에러는 나지 않음.

아래 세 줄은 같은 조건(300건, 같은 검색어 집합, 같은 측정 방법)에서 잰 값. (2026-08-28)
히트와 미스는 분포가 크게 갈리므로 p95를 함께 표기.

| 구분 | 커밋 | 중앙값 | p95 |
|---|---|---|---|
| 캐시 없음 | [`56f0197`](https://github.com/JinsanPark/NewsFinder/commit/56f01973929baad49f4891b3c9d543790236156e) | 226.4 ms | 268.6 ms |
| 캐시 히트 | [`8c1cc41`](https://github.com/JinsanPark/NewsFinder/commit/8c1cc41959e1aa1527e9967bf1a4c31e98f59392) | 28.2 ms | 44.8 ms |
| 캐시 미스 | [`8c1cc41`](https://github.com/JinsanPark/NewsFinder/commit/8c1cc41959e1aa1527e9967bf1a4c31e98f59392) | 286.0 ms | 323.3 ms |

히트 시 API 왕복이 통째로 빠져 약 8배 빨라짐.
미스는 캐시 조회와 저장이 추가되어 도입 전보다 오히려 느려짐.

캐시 동작 테스트: [`261491b`](https://github.com/JinsanPark/NewsFinder/commit/261491b7a554683483a3bf60863a9bae6b4e4447)

## L1 메모리 캐시

DB 캐시 앞에 메모리 캐시를 한 겹 더 얹어 3층으로 만듦.

```
L1(메모리) -> DB(query_vector_cache) -> Voyage API
```

`LinkedHashMap`을 상속해 `accessOrder=true`와 `removeEldestEntry`만 재정의한 LRU. 용량 100.
싼 곳부터 조회하고 없을 때만 다음 층으로 내려가므로, API 호출은 맨 아래 한 곳에서만 일어남.
L1에는 DB에서 찾았을 때와 API에서 받았을 때 모두 저장함.

L1의 키는 정규화된 검색어 하나. DB와 달리 모델명을 포함하지 않는데, **수명이 다르기 때문**.
DB는 프로세스보다 오래 살아 모델 교체 후에도 이전 벡터가 남지만, L1은 재시작하면 비어 있음.

`NewsService`는 변경 없음.

### 경로별 응답 시간

`QueryVectorService.getVector()` 진입 ~ 반환. 경로마다 200회. (2026-09-03)

| 경로 | 중앙값 | p95 |
|---|---|---|
| L1 히트 | 0.0098 ms | 0.0120 ms |
| DB 히트 | 15.2 ms | 20.3 ms |
| API 미스 | 216.5 ms | 243.4 ms |

**L1이 줄인 시간은 15.2 ms.** DB 캐시가 걷어낸 API 왕복 약 204 ms의 7% 수준임.
메모리 조회는 자릿수가 다르지만, 원래 그 자리가 15 ms짜리였으므로 줄일 수 있는 총량이 그만큼임.

전체 응답에서 이 15 ms가 차지하는 비중은 측정 범위 밖.
`getVector()` 안만 쟀고 브라우저 기준 응답은 재지 않음.

### API 미스 한 번의 구성

같은 실행에서 잰 중첩 구간.

| 구간 | 중앙값 | p95 |
|---|---|---|
| Voyage API 왕복 | 184.8 ms | 207.0 ms |
| 캐시 저장 | 23.5 ms | 38.8 ms |
| 나머지 (정규화 + 캐시 조회 + L1 저장) | 6.9 ms | 9.9 ms |
| 전체 | 216.5 ms | 243.4 ms |

구간 합 215.2 ms, 전체 216.5 ms. 각 구간의 중앙값이 서로 다른 요청에서 뽑히므로 정확히 일치하지는 않음.

### 손익분기

```
(캐시 저장 23.5 + 캐시 조회 6.9) ÷ (API 왕복 184.8 + 캐시 저장 23.5) = 14.6%
```

검색 일곱 번 중 한 번이 같은 검색어면 캐시가 이득.
유사도 검색·전송·렌더링은 모든 경로에 동일하게 들어가 상쇄됨.

캐시 저장 23.5 ms는 벡터를 반환한 뒤로 미룰 수 있음.
다만 77.7 ms를 근거로 잡았던 개선안이라 실익이 3분의 1로 줄어든 상태.

### 측정 조건

- 커밋 [`53c3706`](https://github.com/JinsanPark/NewsFinder/commit/53c37069aa5ea2a732ac360d04423ec19f26add7) `_api-miss-v2`는 `save_ms` 구간 추가 후 측정 ([`4bbc4c3`](https://github.com/JinsanPark/NewsFinder/commit/4bbc4c323ba609221bfe5f422c7f9092ce6e1b9c))
- 측정 지점: 서버 내부. `getVector()` 진입 ~ `finally`. 한 요청이 로그 한 줄을 남김
  (`path` / `term` / `save_ms` / `api_ms` / `total_ms`)
- 클라이언트 측정 없음. 경로당 200회를 브라우저로 돌릴 수 없어 서버 내부만 측정
- 입력: [검색어 200개](../data/search_terms_200.md)
- 통계: 중앙값과 p95(nearest-rank). 워밍업·실패 외 이상치 제거 없음
- news 300건 / L1 용량 100 / `spring.jpa.show-sql=false`
- L1 캐시 검색은 101 ~ 200번 까지 검색어를 순차적으로 2번 반복시킴
- 인덱스 `news_embedding_hnsw` 존재하나 이번 측정은 `query_vector_cache`만 조회하므로 무관

경로별 초기화 방법이 다름. **앱 재시작은 L1만 비우고 DB 캐시는 비우지 않음.**

| 경로 | 초기화 | 방법 |
|---|---|---|
| API 미스 | DB 캐시 비움 + 앱 재시작 | 200개를 1회씩. 매 실행이 처음이어야 하므로 반복·워밍업 없음 |
| DB 히트 | 앱 재시작만 | 위 측정이 채운 200개를 사용. 용량 100 < 200이라 L1은 계속 빗나감 |
| L1 히트 | 없음 (DB 히트 측정 직후) | L1에 남아 있는 마지막 100개를 2바퀴 |

원자료: `data/raw/2026-09-03_api-miss.csv`, `_db-hit.csv`, `_l1-hit.csv`, `_api-miss-v2.csv`

## 2026-08-28 측정 정정

캐시 도입 직후 잰 구간 값이 재측정에서 크게 달라짐.

| 구간 | 2026-08-28 | 2026-09-03 |
|---|---|---|
| 정규화 + 캐시 조회 | 12.1 ms | 6.9 ms |
| Voyage API 왕복 | 197.1 ms | 184.8 ms |
| 캐시 저장 | **77.7 ms** | **23.5 ms** |
| 손익분기 히트율 | 32.7% / 23.1% | 14.6% |

옛 값이 왜 그 숫자였는지는 확인할 수 없음. 확인되는 것은 **검증이 불가능하다는 사실**뿐임.

- 세 구간을 서로 다른 요청·다른 시점에서 따로 측정. 그래서 구간 합과 전체가 30 ms 어긋나 있었음
- 계측 코드가 커밋에 남지 않아 재현 불가. `8c1cc41`의 `getVector()`에는 계측이 한 줄도 없음
- 같은 표에 대해 이 문서와 [블로그 6편](https://jinsanpark.github.io/posts/Embedding-Project-6/)이
  서로 다른 측정 지점을 기재하고 있었음

2026-09-03 측정은 계측이 코드에 남아 있고, 한 요청이 로그 한 줄로 기록되며, 구간 합이 전체와 1.3 ms 안에서 맞음.


## 측정 환경

- 애플리케이션: 데스크탑에서 실행 (Ryzen 7 7800X3D / 32GB / Windows 11)
- **캐시 없음 / 자바 캐시**: H2 (임베디드, 앱과 동일 프로세스), JVM 힙 기본값 (32GB 기준 최대 약 8GB)
- **pgvector / pgvector + 인덱스 / 검색어 벡터 캐시**: PostgreSQL 17.10 + pgvector 0.8.3.
  랩탑(Ryzen 7 5800H / 32GB / SSD)에서 도커로 실행. 데스크탑과 같은 공유기, 와이파이 연결
- 임베딩: Voyage AI `voyage-4-lite`, 1024차원
- HNSW: 파라미터를 튜닝하지 않고 기본값 사용 (`m=16`, `ef_construction=64`, `hnsw.ef_search=40`)
- 2026-08-28까지의 측정: 브라우저 개발자도구 Network 탭의 Total,
  [검색어 50개](../data/search_terms.md) × 5회의 중앙값.
  캐시 미스는 중복을 피하기 위해 무작위 문자열 550개를 1회씩
- 2026-09-03 측정: 서버 내부 로그. 브라우저 Network 탭을 쓰지 않음. 조건은 위 '측정 조건' 참고

H2와 PostgreSQL은 실행 위치가 달라 조건이 동일하지 않음.
H2는 앱과 같은 프로세스라 네트워크 비용이 없다는 점에서 자바 구현 쪽에 유리한 조건.
다만 300건 구간은 API 대기가 지배적이라 H2와 PostgreSQL의 DB 왕복 차이가 드러나지 않음.

## 한계

- **측정 시점이 단계마다 다름.** Voyage API 왕복이 측정 세션에 따라 183~197 ms로 흔들리는 것을 확인했으므로,
  서로 다른 날 잰 값의 차이를 개선 효과로 읽으면 안 됨.
  같은 세션에서 조건만 바꿔 잰 것은 검색어 벡터 캐시의 세 줄과 L1 메모리 캐시의 경로별 표뿐임.
  건수별 비교표(300 / 2,400 / 19,200)는 이 문제를 안고 있어 한 번에 다시 측정할 필요가 있음.
- **2026-08-28 측정과 2026-09-03 측정은 경계가 다름.** 앞의 것은 브라우저 Network 탭 기준(전체 응답),
  뒤의 것은 `getVector()` 안만 잰 값. 두 표의 숫자를 직접 빼거나 비교하면 안 됨.
- 데이터가 300종류를 복제한 것이라 벡터 분포가 실제보다 단순함.
  전건 스캔 계열은 영향이 없지만, HNSW는 분포를 타므로 실제보다 유리하게 측정됐을 수 있음.
- 재현율: **300건 기준**, [같은 검색어 50개](../data/search_terms.md)로 인덱스 적용 전후 상위 10건을 비교.
  500건 중 집합 불일치 0건. 1개('경제')에서 8·9위 순서만 교차했고 두 항목의 점수 차는 1e-4 수준.
  단, 300건에서는 애초에 인덱스가 사용되지 않으므로 **두 조건이 사실상 같은 실행 계획이었음.**
  같은 것을 두 번 비교한 셈이므로 인덱스 정확도의 근거가 되지 못하며,
  순서가 교차한 1건은 두 번 측정하는 사이 검색어 임베딩이 미세하게 달라진 결과로 보는 것이 타당함.
  속도를 측정한 19,200건은 복제 데이터라 재현율 검증에 부적합.
- 2026-09-03 측정은 실제 검색어 200개를 사용했으나, 그중 하나를 중복 때문에 교체함.
