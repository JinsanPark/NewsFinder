# 임베딩 검색 프로그램

> 시작: [코사인 유사도와 벡터 검색](https://jinsanpark.github.io/posts/Embedding-Project/)

뉴스 기사를 임베딩해서 의미로 검색하는 웹 애플리케이션.
"코스피 하락"으로 검색하면 그 단어가 없는 "사이드카 이틀 연속 발동" 같은 기사도 찾아준다.
학습 목적의 개인 프로젝트로, 기사 데이터는 저작권 문제를 피하기 위해 더미 데이터를 사용.

Spring Boot / PostgreSQL + pgvector / Voyage AI 임베딩.

## 성능 개선 요약

300건 기준, 검색 한 번의 응답 시간.

| 단계 | 응답 시간 | 커밋 |
|---|---|---|
| 최초 — 매 검색마다 전건 조회 + 파싱 | 225.3 ms | [`c64e9bd`](https://github.com/JinsanPark/NewsFinder/commit/c64e9bd2b9e0b7a8c2a83118a8d1b9617c3e4828) |
| pgvector로 계산 이관 | 196.8 ms | [`2ae30ab`](https://github.com/JinsanPark/NewsFinder/commit/2ae30abc6c47732c82fbca1910143c5b033691d5) |
| 검색어 벡터 캐시 (히트) | 28.2 ms | [`8c1cc41`](https://github.com/JinsanPark/NewsFinder/commit/8c1cc41959e1aa1527e9967bf1a4c31e98f59392) |

적재는 배치 요청으로 58.6초 → 3.5초.

⚠️ 위 세 값은 **측정 시점이 서로 다르다.** 응답의 대부분을 차지하는 Voyage API 왕복이
측정할 때마다 183~197 ms 사이로 흔들리므로, 단계 간 차이를 그대로 개선폭으로 읽으면 안 된다.
같은 세션에서 조건만 바꿔 잰 비교는 [검색어 벡터 캐시](#검색어-벡터-캐시) 섹션뿐이다.

## 실행

환경변수: `VOYAGE_API_KEY`, `DB_HOST`, `DB_USERNAME`, `DB_PASSWORD`

1. postgres 실행 — `pgvector/pgvector` 이미지 사용, DB 생성 후 `CREATE EXTENSION vector;`
2. 아래 인덱스 생성
3. `init` 프로파일로 실행하면 `data/news_articles_dummy.json`을 적재 (최초 1회)
4. 프로파일 없이 실행하면 검색 서버

```sql
CREATE INDEX news_embedding_hnsw ON news USING hnsw (embedding vector_cosine_ops);
```

이 인덱스는 코드로 관리되지 않으므로 새 환경에서는 직접 실행해야 함.

## 검색 성능 - 캐시, pgvector, 인덱스

> 과정: [캐시로 성능 향상 시키기?](https://jinsanpark.github.io/posts/Embedding-Project-3/) · [pgvector, 계산을 DB한테 떠넘기기](https://jinsanpark.github.io/posts/Embedding-Project-4/) · [검색 성능 측정](https://jinsanpark.github.io/posts/Embedding-Project-5/)

더미 기사 300건을 복제해 2,400건, 19,200건으로 늘려가며 측정.

| 방식 | 커밋 | 300건 | 2,400건 | 19,200건 |
|---|---|---|---|---|
| 캐시 없음 (매 검색마다 전건 조회 + 파싱) | [`c64e9bd`](https://github.com/JinsanPark/NewsFinder/commit/c64e9bd2b9e0b7a8c2a83118a8d1b9617c3e4828) | 225.3 ms | 427.2 ms | 2,136.8 ms |
| 자바 메모리 캐시 | [`d234a6a`](https://github.com/JinsanPark/NewsFinder/commit/d234a6aeb6224f504666894c63bcd84d4d84bb67) | 196.7 ms | 239.8 ms | 525.2 ms |
| pgvector | [`2ae30ab`](https://github.com/JinsanPark/NewsFinder/commit/2ae30abc6c47732c82fbca1910143c5b033691d5) | 196.8 ms | 211.2 ms | 287.4 ms |
| pgvector + HNSW 인덱스 | [`56f0197`](https://github.com/JinsanPark/NewsFinder/commit/56f01973929baad49f4891b3c9d543790236156e) + 위 인덱스 | — | — | 209.2 ms |

인덱스 측정은 19,200건만 수행.
응답 시간에는 검색어를 벡터로 바꾸는 Voyage API 왕복이 포함되어 있음. (아래 참조)

### 300건에서는 인덱스를 쓰지 않는 것이 맞다

`EXPLAIN ANALYZE`로 확인한 결과, 300건에서는 플래너가 HNSW 인덱스를 선택하지 않고 전건 스캔을 택한다.
`WHERE` 절을 제거해도 동일하므로 쿼리 형태의 문제가 아니라 **데이터가 작아서** 내린 판단이다.

```
Seq Scan on news  (cost=0.00..37.75 rows=300)
Execution Time: 2.475 ms
```

`enable_seqscan = off`로 인덱스 사용을 강제하면 계획은 바뀌지만 훨씬 느려진다.

```
Index Scan using news_embedding_hnsw on news  (actual time=142.067..142.139 rows=10)
```

| | 시간 |
|---|---|
| Seq Scan (플래너 선택) | 2.475 ms |
| Index Scan (강제) | 142 ms |

**60배 차이다.** 인덱스를 쓸 수 없는 상태가 아니라, 쓰지 않는 쪽이 맞는 상황이다.
300건 규모에서는 HNSW 그래프를 타는 비용이 전건 스캔보다 크다.

> 강제 실행 시 `Execution Time`은 948 ms로 찍히는데, 그중 255 ms는 JIT 컴파일이다.
> `enable_seqscan = off`가 Seq Scan을 금지하는 대신 **비용에 100억을 더하는** 방식이라
> 총비용이 JIT 발동 임계값(`jit_above_cost`)을 넘어버린 것으로, 실제 서비스에서는 발생하지 않는다.
> 따라서 비교 기준은 `Execution Time`이 아니라 Index Scan 노드 시간이다. 강제 실행은 1회 측정.

19,200건에서 287.4 → 209.2 ms로 줄어든 것은 인덱스가 사용된 결과로 보이나, 해당 규모에서는 아직 실행 계획을 확인하지 않았다.

### 검색 한 번의 구성 (300건, 캐시 도입 전)

전체 응답은 브라우저 Network 탭 기준, API 구간은 서버 내부 측정, 쿼리 실행은 `EXPLAIN ANALYZE` 기준.

| 구간 | 시간 | 비중 |
|---|---|---|
| Voyage API 왕복 (검색어 임베딩) | 197.1 ms | 87% |
| 앱↔postgres 왕복, 1024차원 벡터 전송, 결과 매핑, 렌더링 | 약 28 ms | 12% |
| DB 쿼리 실행 | 2.5 ms | 1% |
| 합계 | 226.4 ms | |

**DB가 계산에 쓰는 시간은 전체의 1%다.**
별도로 `SELECT 1`을 실행한 왕복 기준선은 약 7ms (DBeaver 기준, 클라이언트가 달라 정밀 비교는 아님).

이 규모에서는 계산 방식(자바 / pgvector / 인덱스)을 바꿔도 얻을 수 있는 여지가 거의 없다.
300건 구간에서 세 방식이 196~225 ms로 비슷했던 이유이기도 하다.

### 건당 비용

API 왕복은 건수와 무관한 고정 비용이므로, 두 지점의 차이로 산출.

```
(19,200건 값 − 2,400건 값) ÷ 16,800
```

| 방식 | 건당 |
|---|---|
| 캐시 없음 (조회 + 파싱 + 계산) | 101.8 μs |
| 자바 캐시 (계산만) | 17.0 μs |
| pgvector (DB 스캔) | 4.5 μs |

셋 다 전건 스캔이므로 O(n). 상수만 다름.

단, 이 산출은 두 지점의 차이에서 API 왕복이 상쇄된다는 전제 위에 있는데,
두 측정이 같은 세션이 아니라면 API 변동(183~197 ms 관측)이 그 차이에 남는다.
차이가 클수록 영향이 작아지므로 캐시 없음(1,709.6 ms)은 견고하지만,
**pgvector는 두 지점 차이가 76.2 ms에 불과해 4.5 μs를 단정하기 어렵다.**

## 검색어 벡터 캐시

> 과정: [벡터 재활용](https://jinsanpark.github.io/posts/Embedding-Project-6/)

응답 시간의 87%가 검색어 임베딩 API 대기였으므로, 한 번 만든 검색어 벡터를 DB에 저장해 재사용.
`(정규화된 검색어, 모델명)`을 키로 조회하고, 캐시에 있으면 API를 호출하지 않음.
검색어는 `NFC → 앞뒤 공백 제거 → 연속 공백 축약 → 소문자` 순으로 정규화하며, 키와 API 입력에 같은 문자열을 사용.

모델명을 키에 포함시킨 이유는, 모델을 교체했을 때 이전 모델이 만든 벡터가 조용히 재사용되는 것을 막기 위함.
차원 수만 같으면 유사도 계산이 오류 없이 수행되므로 결과만 어긋나고 에러는 나지 않는다.

**아래 세 줄은 같은 조건(300건, 같은 검색어 집합, 같은 측정 방법)에서 잰 값이다.**
히트와 미스는 분포가 크게 갈리므로 p95를 함께 표기.

| 구분 | 커밋 | 중앙값 | p95 |
|---|---|---|---|
| 캐시 없음 | [`56f0197`](https://github.com/JinsanPark/NewsFinder/commit/56f01973929baad49f4891b3c9d543790236156e) | 226.4 ms | 268.6 ms |
| 캐시 히트 | [`8c1cc41`](https://github.com/JinsanPark/NewsFinder/commit/8c1cc41959e1aa1527e9967bf1a4c31e98f59392) | 28.2 ms | 44.8 ms |
| 캐시 미스 | [`8c1cc41`](https://github.com/JinsanPark/NewsFinder/commit/8c1cc41959e1aa1527e9967bf1a4c31e98f59392) | 286.0 ms | 323.3 ms |

히트 시 API 왕복이 통째로 빠져 약 8배 빨라짐.
미스는 캐시 조회와 저장이 추가되어 도입 전보다 오히려 느려짐.

캐시 동작 테스트: [`261491b`](https://github.com/JinsanPark/NewsFinder/commit/261491b7a554683483a3bf60863a9bae6b4e4447)

### 캐시 미스 한 번의 구성

서버 내부 측정 550회의 중앙값.

| 구간 | 시간 |
|---|---|
| 정규화 + 캐시 조회 | 12.1 ms |
| Voyage API 왕복 | 197.1 ms |
| 캐시 저장 | 77.7 ms |

측정 지점: `QueryVectorService.getVector()` 진입 / `embedQuery()` 전후 / `save()` 직후.

늘어난 약 90 ms는 캐시 조회와 저장 비용이며, API가 느려진 것이 아니다.
같은 세션에서 잰 API 왕복 197.1 ms는 캐시 없음(226.4 ms) 측정 때와 동일한 값이다.

구간별 중앙값의 합은 전체 중앙값과 일치하지 않는다. 각 구간의 중앙값은 서로 다른 요청에서 뽑힌 값이므로 비중 파악용으로만 볼 것.

### 손익분기

유사도 검색은 히트·미스·캐시 없음 모두에 동일하게 포함되므로 계산에서 상쇄된다.

```
손익분기 히트율 = (캐시 저장 + 캐시 조회) ÷ (API 왕복 + 캐시 저장)
                = (77.7 + 12.1) ÷ (197.1 + 77.7)
                = 32.7%
```

실측값(28.2 / 286.0 / 226.4)으로 풀면 **23.1%**.

```
28.2 × h + 286.0 × (1 − h) = 226.4
h = 59.6 ÷ 257.8 = 0.231
```

⚠️ **두 식은 대수적으로 같은 식이므로 원래 같은 값이 나와야 한다.**
유사도 검색·전송·렌더링 비용은 세 조건 모두에 동일하게 들어가 상쇄되기 때문이다.
그런데 실측값은 이 관계를 만족하지 않는다.

```
미스 − 캐시없음 = 59.6 ms      캐시 저장 + 캐시 조회 = 89.8 ms    (30 ms 어긋남)
미스 − 히트     = 257.8 ms     API 왕복 + 캐시 저장  = 274.8 ms   (17 ms 어긋남)
```

세 조건을 서로 다른 시점에, 전체는 브라우저 기준으로 구간은 서버 내부 기준으로 측정한 탓으로 보인다.
한 세션에서 같은 방법으로 다시 재기 전까지 이 차이는 설명되지 않으므로,
**32.7%와 23.1%는 대략 20~35% 구간을 가리키는 값으로만 받아들일 것.**

다만 **API 왕복과 캐시 저장이 건수와 무관한 고정 비용**이라는 점은 두 식 모두에서 동일하므로,
데이터가 늘어도 이 비율 자체는 거의 변하지 않는다.

개선 여지: 캐시 저장 77.7 ms는 벡터를 반환한 뒤로 미룰 수 있다.
응답 경로에서 빼면 미스도 200 ms 초반으로 내려간다.

- **측정 시점이 단계마다 다르다.** Voyage API 왕복이 측정 세션에 따라 183~197 ms로 흔들리는 것을 확인했으므로,

- 재현율: **300건 기준**, [같은 검색어 50개](data/search_terms.md)로 인덱스 적용 전후 상위 10건을 비교.
  500건 중 집합 불일치 0건. 1개('경제')에서 8·9위 순서만 교차했고 두 항목의 점수 차는 1e-4 수준.

  같은 것을 두 번 비교한 셈이므로 인덱스 정확도의 근거가 되지 못하며,
  순서가 교차한 1건은 두 번 측정하는 사이 검색어 임베딩이 미세하게 달라진 결과로 보는 것이 타당하다.
  속도를 측정한 19,200건은 복제 데이터라 재현율 검증에 부적합.
